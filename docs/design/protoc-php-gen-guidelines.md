# Рекомендации по `protoc-php-gen`

Этот документ фиксирует правила работы с внутренним генератором `tools/protoc-php-gen` и связанными с ним PHP attributes.

## Зачем существует генератор

В проекте есть задача связать три мира:

- доменные PHP-классы;
- protobuf message classes;
- storage/runtime-friendly hydrator mapping.

`protoc-php-gen` нужен именно для системного решения этой задачи, а не для разовых хаков.

## Когда использовать генератор

Использовать генератор нужно, когда:

- доменная сущность должна стабильно маппиться в protobuf message;
- нужно избежать ручного копирования однотипного mapping-кода;
- структура класса хорошо выражается через декларативные метаданные;
- маппинг должен быть воспроизводимым и проверяемым.

Не стоит использовать генератор, если задача локальная, одноразовая и не формирует устойчивую модель проекта.

## Базовые правила

### 1. Domain-класс остаётся источником бизнес-структуры

Генератор не должен диктовать бизнес-модель. Он должен обслуживать её.

### 2. Mapping metadata должны быть минимальными и декларативными

Атрибуты типа `ProtoMapping` и `ProtoField` должны описывать:

- во что маппится класс;
- как называется поле;
- есть ли специальная обработка типа.

Они не должны превращаться в язык бизнес-логики.

### 3. Генератор не должен маскировать плохую архитектуру

Если для генерации нужны многочисленные исключения, if-ветки и special cases, это сигнал проблемы в модели, а не повод усложнить generator.

### 4. Generated code должен быть одноразово воспроизводимым

Любой разработчик или LLM должны понимать:

- из каких входов генерируется код;
- в какие каталоги попадает результат;
- какую команду нужно запустить после изменений.

## Как размечать классы

Принцип на примере:

- на классе — `ProtoMapping(class: '...')`
- на свойствах — `ProtoField(name: '...')`
- для специальных преобразований — минимально необходимые `type` hints, например `json` или `datetime`

Хорошая разметка:

- повторяет структуру данных;
- не содержит лишней логики;
- согласована с именами в `.proto`.

Плохая разметка:

- требует знания десятков скрытых правил;
- кодирует исключения для одного узкого кейса;
- скрывает смысл модели за генераторными деталями.

## Где должна жить логика преобразования

### В генераторе допустимо

- читать метаданные;
- строить descriptor model;
- генерировать повторяемый технический код;
- приводить имена полей и типы по формальным правилам.

### В генераторе недопустимо

- добавлять доменную бизнес-логику;
- принимать решение за application/service слой;
- вшивать ad-hoc обходы под частный кейс;
- плодить special handling без общего правила.

## Отношение к hydrator-слою

Сейчас в проекте есть два направления:

- `ReflectionHydrator` как основной runtime hydrator;
- `CodeGeneratingHydrator` как более производительное направление развития.

Любые изменения вокруг `protoc-php-gen` должны учитывать этот выбор.

Перед расширением генератора стоит ответить на вопросы:

- он генерирует код для production runtime или только для build-time tooling;
- generated hydrators становятся canonical path или остаются опциональной оптимизацией;
- reflection path остаётся fallback или подлежит удалению.

## Правила для LLM при изменениях

Если LLM меняет класс с `ProtoMapping`/`ProtoField`, она должна:

1. проверить связанный protobuf message;
2. проверить, не сломается ли генерация mapper/hydrator кода;
3. перегенерировать артефакты, если это требуется;
4. убедиться, что mapping по-прежнему выражает общую модель, а не частный случай.

## Антипаттерны

- Добавление новых атрибутов ради одного edge case.
- Условная генерация под конкретный класс без обобщаемого правила.
- Размещение generator-specific logic прямо в domain service.
- Ситуация, где без чтения исходников генератора невозможно понять, как поле будет маппиться.

## Критерий хорошего решения

Хорошее решение вокруг `protoc-php-gen`:

- сокращает ручной boilerplate;
- не размывает архитектурные границы;
- остаётся детерминированным;
- объяснимо по документации без чтения всего генератора целиком.
