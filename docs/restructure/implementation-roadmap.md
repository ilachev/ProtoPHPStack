# Roadmap реализации шаблона

Этот документ описывает практический путь от текущего репозитория к целевому `production-ready` шаблону на чистом PHP с vertical slices архитектурой.

## Общая стратегия

Реализация должна идти поэтапно. Цель — не "переписать всё", а перевести проект в новую архитектуру так, чтобы на каждом этапе он оставался понятным и проверяемым.

## Этап 1. Зафиксировать target state

Цель:

- формально описать vision;
- описать target architecture;
- описать roadmap миграции.

Результат:

- LLM и человек понимают, какой именно шаблон мы строим.

Статус:

- выполняется сейчас.

## Этап 2. Выделить platform core

Нужно определить и минимизировать набор truly shared технических компонентов:

- bootstrap;
- HTTP abstractions;
- pipeline;
- routing runtime;
- storage core;
- logging;
- cache;
- config loading.

На этом этапе ещё не обязательно переносить всё по новым директориям, но уже нужно определить, что является `Platform`, а что нет.

## Этап 3. Выделить первые feature slices

Рекомендуемый порядок:

1. `Home` как reference slice;
2. `Session` как первый реальный production slice;
3. `Stats` как cross-cutting feature рядом с session/runtime;
4. `Auth` как новый полноценный slice, а не только proto contract.

Критерий успеха:

- feature можно читать изолированно;
- её код не размазан по всему проекту.

## Этап 4. Пересобрать bootstrap под modules

Нужно уйти от ощущения, что приложение собирается только через длинный список сервис-провайдеров.

Целевая модель:

- platform bootstraps itself;
- modules регистрируются явно;
- router/pipeline получают зависимости из модулей и platform.

Это не обязательно означает полный отказ от контейнера. Это означает, что структура приложения не должна быть скрыта внутри контейнера.

## Этап 5. Выровнять transport contracts и runtime

На этом этапе нужно устранить несоответствия:

- либо реализовать `AuthHandler` и связанный flow;
- либо временно убрать auth из публичной поверхности;
- привести routes, OpenAPI и runtime к одному состоянию.

Пока этого нет, шаблон нельзя считать production-ready.

## Этап 6. Упростить инфраструктурный хвост

Нужно принять решения по текущим спорным зонам:

- оставить только PostgreSQL или сохранить SQLite как строго ограниченный dev/test инструмент;
- определить судьбу `ReflectionHydrator`;
- определить судьбу `CodeGeneratingHydrator`;
- определить роль `tools/protoc-php-gen` в целевом шаблоне.

На этом этапе важно удалять архитектурный шум, а не накапливать compatibility layers.

## Этап 7. Собрать reference implementation

Когда platform и slices стабилизированы, в репозитории должен остаться маленький, но законченный reference backend:

- `Home` как простой публичный endpoint;
- `Session` как production-grade slice;
- `Auth` как полноценный пример защищённого feature flow;
- `Stats` как пример observability feature.

Такой reference implementation нужен не ради продукта, а как executable documentation шаблона.

## Этап 8. Финализировать developer/LLM ergonomics

Итоговый шаблон должен давать быстрый ответ на вопросы:

- где создавать новую feature;
- где размещать migration;
- как подключать route;
- как писать integration test;
- как регенерировать артефакты;
- какой checklist нужен перед merge.

## Критерии завершённости шаблона

Шаблон можно считать реализованным, если:

- структура репозитория feature-first;
- platform слой мал и стабилен;
- runtime не зависит от framework;
- контракты и runtime согласованы;
- новый slice можно добавить по понятному шаблону;
- документация объясняет систему без чтения всего кода;
- `task verify` остаётся или становится основным надёжным quality gate.

## Практический следующий шаг

После фиксации vision и target architecture следующий полезный шаг — подготовить конкретный план первого структурного переноса:

1. определить будущие каталоги `src/Modules` и `src/Platform`;
2. перенести `Home` в первый reference slice;
3. выделить `Session` в самостоятельный slice;
4. только затем пересобирать bootstrap и DI wiring.
