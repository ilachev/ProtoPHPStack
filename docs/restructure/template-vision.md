# Vision шаблона

Этот документ фиксирует официальную цель проекта.

## Цель проекта

Проект должен стать `production-ready` шаблоном для backend-разработки на чистом PHP, без framework-зависимости и без архитектурной привязки к тяжёлым внешним библиотекам.

Шаблон должен давать:

- предсказуемую и простую архитектурную основу;
- минимальный runtime footprint;
- понятную структуру для LLM и человека;
- возможность развивать реальные production-сервисы без последующего переписывания шаблона "с нуля".

## Что означает "чистый PHP"

Под "чистым PHP" в этом проекте понимается:

- отсутствие зависимости от фреймворка;
- отсутствие library-first архитектуры, где структура приложения диктуется внешним пакетом;
- опора на стандартный PHP, простые interfaces и локальный код проекта;
- использование внешних библиотек только там, где они дают конкретную инфраструктурную ценность и не диктуют форму всей системы.

Иначе говоря: библиотека может быть технической деталью, но не каркасом приложения.

## Что означает "production-ready"

Шаблон считается production-ready, если он из коробки задаёт:

- чёткие модульные границы;
- стабильный request lifecycle;
- ошибкоустойчивую конфигурацию и bootstrap модель;
- понятный logging/observability baseline;
- миграции и работу с PostgreSQL;
- удобный quality gate;
- предсказуемый code generation pipeline, если он сохраняется;
- понятную точку расширения для новых фич.

Production-ready здесь не означает "содержит все фичи любого продукта". Это означает, что архитектурная основа годится для реального сервиса и не выглядит как demo-only заготовка.

## Архитектурная цель

Основная архитектурная цель — `vertical slices architecture`.

Это значит:

- код должен группироваться по feature/capability;
- feature должна включать свои use cases, handlers, domain services, repositories contracts и transport mapping;
- shared platform слой должен быть маленьким и техническим;
- platform не должен размывать feature-модули.

## Предпочтительная модель

Целевой шаблон должен быть устроен так:

- `modules/*` — продуктовые vertical slices;
- `platform/*` — HTTP, storage, cache, logging, bootstrap, routing и другие инфраструктурные механизмы;
- `protos/*` или другой transport contract layer — отдельный источник истины для API, если protobuf остаётся;
- `tools/*` — build/code generation tooling, отделённый от runtime.

## Не-цели

Проект не должен стремиться быть:

- ещё одним микро-фреймворком общего назначения;
- набором unrelated utilities;
- песочницей для случайных экспериментов;
- шаблоном, где каждая подсистема живёт по отдельным правилам.

## Принципы проектирования

### 1. Feature-first structure

Новая функциональность должна добавляться как новый slice, а не размазываться по десяткам технических директорий.

### 2. Small platform core

`platform` должен быть небольшим, стабильным и reused между slices.

### 3. No framework gravity

Внешние пакеты допустимы только как адаптеры, а не как архитектурные центры притяжения.

### 4. Explicit boundaries

Границы между transport, application logic, domain logic и infrastructure должны читаться по структуре каталогов, а не только по договорённости.

### 5. LLM-friendly by design

LLM должна быть способна быстро ответить на вопросы:

- где добавить новый endpoint;
- где лежит бизнес-логика конкретной feature;
- какие артефакты нужно регенерировать;
- какие тесты и проверки надо прогнать.

### 6. Replace accidental complexity with structural clarity

Если кусок кода сложно понять без чтения половины репозитория, значит шаблон организован плохо.

## Стратегическое решение по текущему проекту

Да, эту цель можно зафиксировать и реализовать в текущем репозитории.

Но реализовывать её надо не через косметическую чистку, а через последовательную переработку:

1. зафиксировать target architecture;
2. выровнять модульные границы;
3. отделить demo-функциональность от reusable platform;
4. только затем переносить runtime и storage код в новую структуру.
