# Реструктуризация: базовая карта

Этот документ фиксирует отправную точку перед реструктуризацией.

## Зачем он нужен

Если реструктурировать проект без фиксации текущего состояния, быстро появятся проблемы:

- перенос кода без понимания реальных границ;
- разрыв между `.proto`, routes, OpenAPI и runtime;
- смешивание reusable infrastructure с demo-функциональностью;
- локальные правки без общего плана.

Целевое состояние теперь зафиксировано отдельно в:

- `docs/restructure/template-vision.md`
- `docs/architecture/target-architecture.md`
- `docs/restructure/implementation-roadmap.md`

## Текущее состояние в одной фразе

Проект уже содержит сильный каркас API-шаблона, но его подсистемы пока организованы вокруг технических возможностей, а не вокруг устойчивой модульной структуры.

## Главные структурные проблемы

### 1. Нечёткая цель репозитория

Сейчас репозиторий одновременно играет роли:

- шаблона для новых API-проектов;
- демонстрационного сервиса;
- песочницы для генераторов и hydrator tooling.

Это разные продукты с разным жизненным циклом.

### 2. Модули организованы по техническим каталогам, а не по продуктовым capability

Например:

- sessions были растянуты между `Domain`, `Application/Client`, `Application/Middleware`, `Infrastructure/Storage`, `Infrastructure/DI`;
- routing разбит между proto, generator, config и runtime router;
- hydrator/codegen — отдельная ось, которая пересекает почти все слои.

### 3. Не вся declared API surface реализована

`AuthService` уже существует как контракт, route и OpenAPI, но не как завершённый runtime module.

### 4. Tooling и runtime смешаны в одном уровне важности

`tools/protoc-php-gen`, `bin/generate-routes.php`, domain proto options и runtime hydrator — это один общий контур code generation, но в проекте он документирован слабо и структурно не выделен.

### 5. В проекте есть следы нескольких эволюционных этапов

- PostgreSQL-first стратегия при наличии SQLite слоя;
- reflection hydrator и новый code-generating hydrator;
- generic template code и доменно-специфичные демонстрационные элементы.

## Что не надо делать при реструктуризации

- Не начинать с массового перемещения файлов без фиксации модульной карты.
- Не менять одновременно архитектуру, transport contracts и storage schema без промежуточных checkpoints.
- Не удалять генерацию, пока не описано, чем она заменяется.
- Не оставлять "временно" рассогласованные `.proto` и runtime.

## Рекомендуемый порядок реструктуризации

### Этап 1. Зафиксировать текущую систему

Сделать именно то, с чего начинается работа сейчас:

- описать архитектуру;
- описать request flow;
- описать code generation pipeline;
- описать текущие расхождения и технический долг.

### Этап 2. Выделить целевые модули

Предварительная целевая карта может выглядеть так:

- `modules/home`
- `modules/session`
- `modules/user`
- `modules/auth`
- `platform/http`
- `platform/storage`
- `platform/cache`
- `platform/routing`
- `platform/codegen`

Это не инструкция к немедленному переносу файлов, а рамка для обсуждения.

### Этап 3. Разделить template-core и demo-domain

Нужно решить, что относится к reusable template:

- DI
- HTTP pipeline
- routing
- storage abstractions
- cache
- codegen

И что относится к демонстрационной предметной области:

- home
- session behavior specifics
- auth contracts
- geolocation examples
- stats example

### Этап 4. Выровнять контракты и реализацию

До крупных переносов нужно добиться одного из двух состояний:

- либо auth реализация появляется;
- либо auth контракты временно выводятся из публичной поверхности.

Промежуточное состояние, где контракт есть, а runtime не готов, плохо подходит для долгой жизни репозитория.

### Этап 5. Упростить toolchain

Надо принять решения:

- остаётся ли SQLite;
- остаётся ли reflection hydrator;
- остаётся ли `tools/protoc-php-gen` внутри репозитория;
- какой pipeline генерации считается canonical.

## Практический Definition of Done для хорошей реструктуризации

- LLM может по документации понять, где менять код под новый endpoint.
- LLM может определить, какие артефакты надо регенерировать.
- `.proto`, routes, OpenAPI и runtime согласованы.
- Модульные границы видны по структуре каталогов, а не только по устным договорённостям.
- `task verify` остаётся основным и понятным quality gate.

## Следующий разумный шаг после документации

После добавления этих документов имеет смысл отдельно подготовить целевую модульную карту новой структуры и согласовать её до начала переносов кода.
